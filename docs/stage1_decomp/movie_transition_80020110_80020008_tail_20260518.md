# Movie transition `80020110` / `80020008` tail boundary 2026-05-18

Scope: Stage1 movie / clear-tail transition direct-port boundary. This note records
current IDA evidence only; it does not authorize a Win `PrTransition` visual
fallback.

## Evidence

- Existing export
  `docs/stage1_decomp/ida_export_intro_transition_buffer_ot_800201ac_chain_20260517.txt`
  shows `800201AC(a1,a2,a3,a4)`:
  `8001FFD4(a3)` -> loop `8001EA74(a1,a2)`, `80035560(2)`,
  `8001EBF4()`, `8001F518()` -> `8001FFD4(a4)` ->
  `gp+0xC4 = 190` -> `80020090(a1,a2,8001EA74,8001EBF4)`.
- Existing export
  `docs/stage1_decomp/ida_export_intro_transition_callers_801c4dc4_20260517.txt`
  shows `80020110(a1,a2,a3,a4)` is the same outer shape as `800201AC`, but
  each loop iteration inserts `80027194(30)` before `80035560(2)` and finishes
  via `80020008(a1,a2,8001EA74,8001EBF4)`.
- Current IDA decompile for `80027194` shows the `30` argument is not consumed:
  the function reads `gp+0x1E0`, and when that counter is already `>= 2` it
  calls `80026EF8(dword_8006EC18)` and `80026ECC()`, clears the counter, then
  increments it. `dword_8006EC18` is the compact cue payload
  `{program=0, note=12, key=0x24, volume=0x50}`. Therefore this is a
  three-call cue/flush cadence, not a 30-frame Win transition delay.
- Current IDA decompile for `80020008`:

```c
BOOL __fastcall sub_80020008(
    int a1,
    int a2,
    void (__fastcall *a3)(int, int),
    void (__fastcall *a4)(int))
{
  int v4 = a1;
  int v8 = 0;
  BOOL result;
  do
  {
    a3(a1, a2);
    sub_80027194(30);
    sub_80035560(2);
    a4(v4);
    result = ++v8 < 4;
    a1 = v4;
  }
  while ( v8 < 4 );
  return result;
}
```

## Boundary

- Clear-tail `800201AC(...,6,2,1)` and `800201AC(...,5,1,2)` can run through
  the Movie1 direct transition runtime because their loop/tail semantics are
  already represented by `ResolveTransitionSub800201ACStep(...)` and
  `BuildRuntimeDrawPlan(...)`.
- `80020110(...,2,1,2)` uses the same direct transition runtime with a separate
  variant bit: loop/tail steps append the `80027194` cadence action, the end
  `8001FFD4(a4)` does not force `gp+0xC4=190`, and the 4-frame tail is marked
  as `80020008` rather than `80020090`.
- The Win HAL action for the cadence is limited to the explicit PSX cue payload
  and `80026ECC` audio-driver flush. It does not authorize a Win `PrTransition`
  fallback and does not derive success from renderer state.
