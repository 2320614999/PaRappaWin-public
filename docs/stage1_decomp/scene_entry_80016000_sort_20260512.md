# scene entry high-score bank sort closure: 80016000 / 800164F8

Source: IDA MCP direct decompile/disassembly from `SCUS_941.83`, 2026-05-12.
No build, no runtime replay, no Win-side sorting inference.

## 80016000 sub_80016000

IDA pseudocode:

```c
BOOL __fastcall sub_80016000(int a1, int a2)
{
  BOOL result; // $v0
  int i; // [sp+10h] [+10h]
  int j; // [sp+14h] [+14h]

  for ( i = 0; ; ++i )
  {
    result = i < a2 - 1;
    if ( i >= a2 - 1 )
      break;
    for ( j = i + 1; j < a2; ++j )
    {
      if ( *(_DWORD *)(16 * i + a1 + 12) < *(_DWORD *)(16 * j + a1 + 12) )
        sub_80016D7C(16 * i + a1, 16 * j + a1);
    }
  }
  return result;
}
```

Equivalent typed form, preserving the IDA behavior:

```c
struct HiScoreSlot80016000 {
  char name[12];    // C string region used by strcmp/strcpy.
  int32_t score;    // slot+0x0C, signed compare.
};

BOOL sub_80016000(HiScoreSlot80016000 *base, int count)
{
  BOOL result;

  for (int i = 0;; ++i) {
    result = i < count - 1;
    if (i >= count - 1)
      break;

    for (int j = i + 1; j < count; ++j) {
      if (base[i].score < base[j].score)
        sub_80016D7C(&base[i], &base[j]);
    }
  }
  return result;
}
```

Important assembly corrections:

```asm
80016080: sll     $v0, $v1, 4       ; i * 16
8001608C: addu    $v0, $v1          ; base + i*16
8001609C: sll     $v1, $a0, 4       ; j * 16
800160A8: addu    $v1, $a0          ; base + j*16
800160AC: lw      $v0, 0xC($v0)     ; base[i].score
800160B0: lw      $v1, 0xC($v1)     ; base[j].score
800160B8: slt     $v0, $v1          ; base[i].score < base[j].score
800160BC: beqz    $v0, loc_8001610C
80016104: jal     sub_80016D7C      ; swap full slot payload
```

`80016000` is not a delete/compact routine by itself. It is a descending
selection/bubble-style sort over `count` slots, using signed `s32 score` at
slot offset `+0x0C`. Equal scores are not swapped because the condition is
strict `<`, so ties keep existing relative order for the pairs inspected.

## Swap Helper: 80016D7C

IDA pseudocode:

```c
int __fastcall sub_80016D7C(int a1, int a2)
{
  int v5; // [sp+10h] [+10h]
  _BYTE v6[16]; // [sp+18h] [+18h] BYREF

  v5 = *(_DWORD *)(a1 + 12);
  strcpy(v6, a1);
  *(_DWORD *)(a1 + 12) = *(_DWORD *)(a2 + 12);
  strcpy(a1, a2);
  *(_DWORD *)(a2 + 12) = v5;
  return strcpy(a2, v6);
}
```

This confirms the slot layout used by sort:

```c
struct HiScoreSlot {
  char name[12];  // starts at slot+0, copied with strcpy.
  s32 score;      // slot+12.
};                // sizeof == 16
```

IDA does not bound the `strcpy` in this helper. The destination capacity
implied by the score offset is 12 bytes including the terminator if the score
must remain intact.

## Clear: 800168DC

```c
__int64 sub_800168DC()

  }
```

Assembly correction:

```asm
80016950: li      $at, unk_80094228
8001695C: sw      $zero, 0($at)     ; score at row*64 + slot*16 + 0x0C
```

name first byte to NUL. It does not zero every byte of the 12-byte name region.

## Input/Bank Layout

Bank base:

```c
static constexpr uint32_t kHiScoreBankBase8009421C = 0x8009421C;
static constexpr size_t kHiScoreRowCount = 6;
static constexpr size_t kHiScoreVisibleSlotCount = 3;
static constexpr size_t kHiScorePhysicalSlotCount = 4;
static constexpr size_t kHiScoreRowStride = 64;
static constexpr size_t kHiScoreSlotStride = 16;
static constexpr size_t kHiScoreScratchSlotIndex = 3;
```

Row/slot address:

```c
rowBase(row) = 0x8009421C + row * 64;
slot(row, col) = rowBase(row) + col * 16;
```

Slot fields:

```c
slot + 0x00: char name[12]   // C string region used by strcmp/strcpy.
slot + 0x0C: s32 score       // signed score, compared by 80016000.
slot + 0x10: next slot
```

Scratch slot:

```c
rowBase + 0x30 == slot(row, 3)
0x8009424C == 0x8009421C + 0x30
```

`sub_800164F8(a1)` candidate input:

```c
a1 + 0x01: candidate name/suffix C string start
a1 + 0x14 + row*4: candidate score for row 0..5
```

Display/output relationship from existing IDA-backed `80019284` closure:

```c
a1 + 4876 + row*64 + col*16: output/display name source
a1 + 4888 + row*64 + col*16: output/display score source
format: "%4d %-3.3s"
```

So the bank slot name storage is a C string region up to the slot score at
`+0x0C`, while the high-score display path uses only `%-3.3s`. Treating the
bank name as exactly 3 bytes would lose the `strcmp/strcpy` semantics seen in
`800164F8` and `80016D7C`.

## Sorting / Dedupe / Convergence Rules

Observed rules from IDA:

1. `800164F8` loops 6 high-score rows.
2. For each row, it reads one candidate score from `payload + 0x14 + row*4`.
3. It uses the same candidate name pointer `payload + 1` for every row.
4. It compares the candidate only against the first 3 visible slots.
5. Duplicate means both `strcmp(candidateName, visibleSlotName) == 0` and
   `candidateScore == visibleSlotScore`.
6. If duplicate is found in visible slots 0..2, it does not write scratch and
   does not call `80016000`.
7. If no duplicate is found, it writes candidate to slot 3:
   `slot3.score = candidateScore; strcpy(slot3.name, candidateName);`.
8. It calls `80016000(rowBase, 4)`.
9. `80016000(rowBase, 4)` sorts all 4 physical slots by signed score
   descending.
10. Convergence back to 3 visible slots is by consumers using only slots 0..2.
    The 4th slot remains present in memory after sort; if the scratch record is
    not top-3, it stays in slot 3. If it enters top-3, the previous lowest
    visible record is pushed into slot 3.

This means there is no separate explicit "clear scratch after merge" in
`800164F8` or `80016000`. The fourth slot is a persistent physical overflow
slot for sort convergence, and visibility is defined by later code that reads
3 slots per row.

Implementation notes:

- Represent each row as exactly 4 physical slots x 16 bytes.
- Sort by `score` descending with strict `<`, not `<=`.
- Do not remove or zero slot 3 after sorting unless another PSX function is
  later proven to do so.
- When exporting to the `80019284` table, read only visible slots 0..2.
- Preserve the distinction between `name[12]` storage and `%-3.3s` display.

## Remaining Uncertainty

Still not proven in this closure:

- The producer-side maximum length and filtering rules for the C string at
  `payload + 1`. `800164F8` only proves `strcpy/strcmp` use from that pointer.
- Whether all real card payloads guarantee NUL termination before the score
  area. The slot layout implies this must be true to avoid corrupting score,
  but this needs upstream save-name writer proof.
- Whether any later function outside `80016000/800164F8/800168DC/80019284`
  explicitly sanitizes or clears the retained 4th slot. No such clear is shown
  in the functions above.
- Tie ordering beyond the strict no-swap condition inside this sort. Existing
  slot order is preserved for equal-score comparisons in `80016000`, but any
  upstream insertion order effects must still come from PSX evidence.

Do not replace this with Win-side sorting guesses. The authoritative behavior
for this closure is the IDA-proven bank layout plus `800164F8 -> 80016000 ->
80016D7C` path above.
